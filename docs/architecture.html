Tibia Party Manager

Substitui as planilhas manuais de uma party de Tibia: log de drops, split de loot, timers de boss, calculadoras de tier/charm, histórico de XP e agenda de serviceiros. React 19 + TypeScript + Vite, dado real parcial via Supabase, dois proxies de leitura (TibiaData e a planilha pessoal do usuário) via Vercel Functions.

stack: React 19 · Vite 6 · TypeScript 10 rotas 9 módulos deploy: tibiacontroll.vercel.app repo: elbiojuzao/TibiaControll
⚠ Produção builda a partir da branch main, não da branch de trabalho ativa. Um commit numa feature branch só chega em tibiacontroll.vercel.app depois de um merge (PR) explícito para main — confirmado na prática em 2026-08-09, quando um fix ficou ~10 min "sem efeito" até isso ser percebido.

Alinhamento inferior das 3 colunas (2026-08-25)
Pedido do usuário: "vamos fazer um alinhamento inferior com base na tabela central". Tentativa inicial (CSS puro: flex:1+minHeight:0 nas colunas laterais, contando com align-items:stretch do Grid) não funcionou — confirmado via getBoundingClientRect(), sobrava ~317px vazios embaixo da Coluna 2. Causa: o auto-sizing de linha do CSS Grid usa o conteúdo NATURAL (max-content) de cada item, ignorando que um descendente aninhado (não o item da grade em si) tem overflow:auto — a regra de "automatic minimum size = 0 pra scroll containers" só vale pro próprio item da grade.

Solução final: ResizeObserver medindo a altura RENDERIZADA de verdade da Coluna 2, aplicada como height em px nas Colunas 1/3 — com altura definida (não mais auto), o flex:1/overflow:auto internos passam a cortar/rolar de verdade até bater exato com a Coluna 2. Reage a qualquer mudança futura de conteúdo da Coluna 2 (nº de membros, linhas de Meta XP), não é mais um número fixo "no olho" como o maxHeight:720px/320px anterior.

Guard de mobile — achado testando a 1ª versão no preset mobile: aplicar a altura fixa incondicionalmente criava um vão vazio enorme, já que .responsive-grid empilha tudo em 1 coluna abaixo de 768px (as colunas não ficam mais lado a lado). Corrigido com isDesktopLayout (matchMedia('(min-width: 769px)'), mesmo breakpoint do CSS) — só aplica a altura fixa em desktop; mobile volta a height:auto. Testado em ambos: desktop com as 3 colunas terminando no mesmo pixel exato (gap=0.0), mobile sem vão vazio.

09 Regras de negócio

Split Loot — matchmaking de transferências

  1. Filtra jogadores excluídos
  2. globalBalance = soma dos balances individuais − soma de despesas extras
  3. fairShare = globalBalance ÷ nº de jogadores ativos
  4. Cada jogador vira credor, devedor ou settled (|delta| < 1)
  5. Matchmaking guloso: maior devedor casa com maior credor, repete até zerar — minimiza nº de transferências

Calculadora Tier — árvore de fusão exponencial

Fusão/Convergência sempre consome 2 itens idênticos do mesmo tier — nunca de graça, nem o item que você já tem. fusionsAtThisLevel(toTier) = 2^(targetTier − toTier). Levou 3 rodadas de correção nesta sessão (multiplicador linear → "metade de graça" → árvore exponencial certa) — não reintroduzir modelo linear.

Charm Planner — custo acumulado

cumulativeCost[level-1] já inclui todos os níveis anteriores — não somar cumulativeCost[0]+[1]+[2] pra chegar no nível 3, o valor de [2] já é o total.

Cache de XP — janela das 7h15

O cache local só é considerado "de hoje" a partir das 7h15 — a rotina do usuário grava a XP entre 6h–7h, então um cache feito antes disso (mesmo que já seja "hoje") é tratado como do dia anterior e força nova busca.

Previsão fim de ano — real desde 2026-08-10

Substituiu um script do usuário no Google Apps Script — mesma lógica, fontes diferentes. xpParaNivel(L) = floor((50/3) · (L³ − 6L² + 17L − 12)) é a fórmula oficial de XP-por-nível do Tibia (ex: nível 2 = 100 XP, nível 3 = 200 XP). predictEndOfYearLevel soma XP atual (via Highscores categoria "experience", cacheado 1h por personagem desde 2026-08-14 — o Tibia não expõe XP total na página do personagem) + média diária (xp90Dias ÷ 90, da planilha) × dias restantes até 31/12, e sobe de nível enquanto essa XP prevista bate o próximo patamar. Tudo calculado em services/xp-sheet/level-prediction.ts, sem nenhum fetch novo (reaproveita useMemberLiveStats + useXpSheet).

Peças: (1) menu hambúrguer em AppLayout.tsx — .topbar-menu-btn (☰/✕, só <768px) alterna mobileMenuOpen, troca .topbar-nav pra .open (painel dropdown full-width em coluna); acima de 768px o comportamento é o de sempre, sem custo pro desktop; (2) classes .responsive-grid (empilha 1 coluna) / .responsive-grid-2 (força 2 colunas) adicionadas como className AO LADO do gridTemplateColumns inline já existente em cada página — o !important da media query vence o style inline sem reescrever cada arquivo. .responsive-grid > * { min-width: 0 } foi necessário além disso: sem isso, uma tabela larga dentro do grid item (ex: planilha de membros do Dashboard) força a coluna empilhada a ficar larga do mesmo jeito — o clássico bug de grid/flex ignorando overflow-x:auto de um descendente não-direto; (3) .grid-2col/.grid-3col (formulários/modais) empilham em 1 coluna <768px automaticamente, sem tocar em cada modal; (4) .dashboard-container/.main-content reduzem padding; .page-header ganhou flex-wrap (botão de ação some pra linha de baixo do título); .calendar-header empilha (mês+Hoje em cima, navegação embaixo). Testado em 320/375/768px e 1280px (desktop, sem regressão) — as 10 páginas + hambúrguer + DropFormModal (720px) + modal de dia do Calendário, sem overflow horizontal de página.
  • Scrollbar temática (2026-08-25) — pedido do usuário: "essa barra de scroll cinza ta muito feia vamos dar um jeito nela?". global.css ganhou * { scrollbar-width: thin; scrollbar-color: var(--color-border-strong) var(--color-bg); } + os pseudo-elementos ::-webkit-scrollbar* (Chrome/Edge) aplicados na página inteira — trilho --color-bg, thumb --color-border-strong, thumb no hover --color-accent, no lugar da barra cinza padrão do navegador. .topbar-nav já tinha sua própria versão fina (4px, só horizontal) — continua funcionando por cima, sem conflito.
