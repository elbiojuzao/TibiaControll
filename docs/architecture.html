Tibia Party Manager

Substitui as planilhas manuais de uma party de Tibia: log de drops, split de loot, timers de boss, calculadoras de tier/charm, histórico de XP e agenda de serviceiros. React 19 + TypeScript + Vite, dado real parcial via Supabase, dois proxies de leitura (TibiaData e a planilha pessoal do usuário) via Vercel Functions.

stack: React 19 · Vite 6 · TypeScript 10 rotas 9 módulos deploy: tibiacontroll.vercel.app repo: elbiojuzao/TibiaControll
⚠ Produção builda a partir da branch main, não da branch de trabalho ativa. Um commit numa feature branch só chega em tibiacontroll.vercel.app depois de um merge (PR) explícito para main — confirmado na prática em 2026-08-09, quando um fix ficou ~10 min "sem efeito" até isso ser percebido.

02 Como o dado chega em cada tela

Três mecanismos coexistem, e cada um se comporta diferente. Este é o fato mais importante do projeto pra qualquer sessão futura: nem todo hook segue o padrão repository/mock, e cache não é uniforme entre eles.

Lição crítica — client Supabase é um singleton preguiçoso. getSupabaseClient() só cria o client dentro de cada método, nunca no top-level do módulo. 09 Regras de negócio

Split Loot — matchmaking de transferências

  1. Filtra jogadores excluídos
  2. globalBalance = soma dos balances individuais − soma de despesas extras
  3. fairShare = globalBalance ÷ nº de jogadores ativos
  4. Cada jogador vira credor, devedor ou settled (|delta| < 1)
  5. Matchmaking guloso: maior devedor casa com maior credor, repete até zerar — minimiza nº de transferências

Calculadora Tier — árvore de fusão exponencial

Fusão/Convergência sempre consome 2 itens idênticos do mesmo tier — nunca de graça, nem o item que você já tem. fusionsAtThisLevel(toTier) = 2^(targetTier − toTier). Levou 3 rodadas de correção nesta sessão (multiplicador linear → "metade de graça" → árvore exponencial certa) — não reintroduzir modelo linear.

Charm Planner — custo acumulado

cumulativeCost[level-1] já inclui todos os níveis anteriores — não somar cumulativeCost[0]+[1]+[2] pra chegar no nível 3, o valor de [2] já é o total.

Cache de XP — janela das 7h15

O cache local só é considerado "de hoje" a partir das 7h15 — a rotina do usuário grava a XP entre 6h–7h, então um cache feito antes disso (mesmo que já seja "hoje") é tratado como do dia anterior e força nova busca.

Previsão fim de ano — real desde 2026-08-10

Substituiu um script do usuário no Google Apps Script — mesma lógica, fontes diferentes. xpParaNivel(L) = floor((50/3) · (L³ − 6L² + 17L − 12)) é a fórmula oficial de XP-por-nível do Tibia (ex: nível 2 = 100 XP, nível 3 = 200 XP). predictEndOfYearLevel soma XP atual (ao vivo, via Highscores categoria "experience" — o Tibia não expõe XP total na página do personagem) + média diária (xp90Dias ÷ 90, da planilha) × dias restantes até 31/12, e sobe de nível enquanto essa XP prevista bate o próximo patamar. Tudo calculado em services/xp-sheet/level-prediction.ts, sem nenhum fetch novo (reaproveita useMemberLiveStats + useXpSheet).

10 Problemas conhecidos & pegadinhas

Coisas que já morderam nesta sessão — ler antes de reintroduzir o mesmo padrão.

alto

Login precisa de 3 passos manuais do usuário pra funcionar

Supabase Auth

O código do login (2026-08-14, desenhado pra multi-conta) está pronto e testado (redirecionamento, cadeados na sidebar, erro de credencial inválida — tudo confirmado), mas ninguém consegue entrar E ENXERGAR A CONTA até: (1) rodar supabase/migrations/20260814000000_enable_rls_with_auth.sql no SQL Editor; (2) criar o usuário em Authentication → Users → Add user, com "Auto Confirm User" marcado; (3) rodar o UPDATE (SQL pronto no fim da migration) ligando accounts.user_id a esse usuário. Nenhum pode ser feito por uma sessão do Claude (sem credencial de admin do Supabase). Passo 3 é o mais traiçoeiro: faltando só ele, o login em si funciona, mas a conta fica "órfã" e o RLS não deixa ninguém ver os dados — parece bug, mas é só configuração pendente.

alto

Members precisa da migration + flag antes de ir pro ar

Supabase · módulo Configurações

O módulo Configurações e a HttpMemberRepository (2026-08-14) estão prontos e testados localmente com mock, mas VITE_MEMBER_USE_SUPABASE está false até rodar supabase/migrations/20260814010000_create_members_table.sql no SQL Editor. Enquanto isso, o app lê o array mock fixo (accountId='acc-demo-001'), que não bate com a conta real — Dashboard/Histórico/Histórico de XP aparecem sem nenhum membro em produção (mesmo problema já visto com Account antes do ACCOUNT_USE_SUPABASE). 11 Convenções & env vars

Convenções de produto

  • Nunca excluir dado persistido com 1 clique só — sempre confirmação
  • Ícone de exclusão sempre 🗑️, nunca "✕"
  • Datas em DD/MM/YYYY na UI/domínio; ISO só na borda com Supabase
  • Gold sempre inteiro, formatado pt-BR com prefixo +
  • Nunca commitar/dar push sem confirmação explícita do usuário
  • Toda mudança no app atualiza este HTML e o architecture.json junto — regra permanente do usuário (2026-08-10), não deixar os docs desatualizarem
  • 2 pipelines de ícone diferentes, não confundir: itens de drop vêm de tibia.fandom.com (fetch-item-icons.mjs, resolução dinâmica); runas de charm vêm de tibiawiki.com.br (fetch-charm-icons.mjs, lista fixa)
